Section 1 · Problem & Goal

Make offline work automatic after sign-in — on every Android phone

Decisions Locked · Awaiting Go-Ahead

Today, CaneGuard Mobile bundles on-device AI models (Guard V1 + Classifier V2) and an offline-first SQLite database, yet offline usability breaks before a user even reaches the scanner. Because offline session persistence is tangled with manual opt-in biometric/device unlock, farmers and inspectors on budget or non-biometric phones get signed out mid-field whenever Android reclaims the app from memory.

Current Setup Steps 5 steps Login → Sheet → Account Security → Enable Unlock → OS Prompt → Download Visits
Target Setup Steps 0 extra Sign in once online → offline persistence works immediately on every phone
Biometric Hardware Needed None Decouple persistence from lock; optional lock supports Biometric, Phone PIN, or 4-digit App PIN
Accounts Covered Both roles Field Inspectors (field_reporter) and Farmers (farmer) equally supported
Core Architectural Shift: Decouple "Stay Signed In Offline" from "App Lock"

The root cause of every friction point is that one switch (biometricEnabled) currently controls two unrelated things: (1) whether the session survives an app restart offline, and (2) whether the phone prompts for biometric/lock-screen auth on cold start. Separating them lets every user stay signed in offline automatically after login, while letting optional or role-scoped App Lock adapt gracefully to whatever the phone supports (Biometric → Device PIN → 4-digit CaneGuard PIN).

Section 5 · Selected Architecture

Selected: Option C (Role-Aware Offline Access)

Confirmed

All three options remove biometric hardware as a requirement, eliminate the 5-step Account Security setup maze, fix the 0-visit false readiness alarm, and bring farmers into first-class offline support. They differ only on whether cold-start prompts a local lock by default.

Option A Lowest friction

Seamless Stay-Signed-In + Optional App Lock

Sign in once online → both Farmers and Inspectors resume directly into Home after any offline restart. App Lock (Biometric / Phone PIN / 4-digit CaneGuard PIN) is optional in Settings for shared phones.

  • 0 setup steps on every phone (including no-lock Android devices).
  • Zero unlock friction in bright sun with muddy/gloved hands in the field.
  • Tradeoff: Relaxes security fix #70 for inspectors on unlocked/shared phones — anyone holding an unlocked inspector phone can reopen CaneGuard until logout.
Option C · Selected Confirmed Direction

Role-Aware: Seamless for Farmers, Adaptive Lock for Inspectors

Farmers stay signed in offline silently with zero lock prompts (personal scans never touch office pipelines). Inspectors auto-persist on login with a single adaptive local gate: OS Biometric/PIN if available, or a quick 4-digit CaneGuard PIN on no-lock phones (with an option to turn off if using a dedicated personal phone, or keep on for shared LGU phones).

  • Matches real threat model: Farmers get zero-friction field scanning; office-authorized inspector data & report authoring stay protected on shared/lost phones.
  • 0 setup steps for Farmers and for Inspectors whose phone already has a screen lock; 1 inline 4-digit PIN only if an inspector phone has no screen lock at all.
  • Tradeoff: Slight behavioral difference between roles (clear, simple copy explains why).
Option B Strictest local lock

Auto-Persist + Mandatory Universal Local Lock (Both Roles)

Every account auto-persists on sign-in, and cold-start always prompts: OS Biometric/PIN if the phone has one, or an inline 4-digit CaneGuard Quick PIN setup right after login if the phone has no screen lock.

  • Preserves 100% of security fix #70 ("no silent cold-start restore") across all accounts while still removing biometric hardware barriers.
  • Tradeoff: Adds a 4-digit PIN setup + cold-start unlock prompt for rural farmers who have low security sensitivity and just want to photograph a cane leaf quickly.

Section 6 · Engineering Blueprint

Ordered changes, affected files, and data contracts

Zero breaking backend changes
1

Decouple Session Persistence from Biometrics in tokenStore.ts & AuthProvider.tsx

Replace the binary biometricEnabled gate with two explicit concepts: session persistence (always saved on successful login in SecureStore with AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY) and localLockMode ('none' | 'device' | 'app-pin').

  • On login(): immediately persist MobileSession (including fresh CapabilityGrant) to SecureStore so cold-start offline works from minute one.
  • On cold-start bootstrap: read localLockMode; if 'none', hydrate directly; if 'device', run one LocalAuthentication prompt (biometric OR device PIN); if 'app-pin', show CaneGuard's 4-digit Quick PIN unlock screen before reading the session.
  • Auto-migrate existing installations seamlessly: if legacy BIOMETRIC_ENABLED_KEY === 'true', map to localLockMode = 'device' without forcing re-login!
  • On explicit logout() or authoritative 401/403 revocation: wipe session, localLockMode, and App PIN hash (fail-closed, unchanged).
2

Add Universal 4-Digit Quick PIN Service & Remove the Disable-Unlock Logout Trap

Create a lightweight appPinAuth.ts service using expo-crypto (already available or lightweight pure-JS PBKDF2/SHA-256 with random 16-byte salt) stored in SecureStore.

  • Store { saltHex, hashHex, failedAttempts, lockedUntil } in SecureStore — never plaintext, never stored in AsyncStorage or SQLite.
  • After 5 failed PIN attempts, wipe the cached session and require online password login (prevents brute-force on a lost phone!).
  • Add a clean native formSheet (app-pin-setup.tsx) using SheetScreen for setting/changing the 4-digit PIN, and an unlock screen integrated with login.tsx (with "Use password instead" escape hatch).
  • Fix AccountSecurityScreen: toggling App Lock off verifies current lock/PIN locally instead of calling disableBiometricApi + logging the user out! (Keep disableBiometric API helper intact only if needed for server audit, or stop invoking forced logout.)
3

Fix Offline Readiness Logic & Retire ReadyForFieldSheet Maze

Stop treating 0 assigned visits or missing biometric hardware as "Not ready for offline work".

  • Update deriveReadiness() in src/features/auth/domain/sessionState.ts:
    • Remove 'turn-on-biometric' as a blocking readiness step (session persistence is now automatic!).
    • Decouple cachedVisits === 0 from core offline readiness: show visit count neutrally (e.g., "0 office visits assigned — you can still scan & file field reports offline") rather than an amber failure state.
    • Only flag not-ready when action is genuinely needed: 'confirm-access' (inspector 72h carry-over <12h or expired), 'sign-in' (session expired), or 'ask-office' (capability revoked).
  • Retire the post-login ReadyForFieldSheet detour on login.tsx (for Option C/B, only show the 1-step 4-digit PIN sheet if an inspector signs in on a phone with SecurityLevel.NONE).
  • Give Farmers a calm, bilingual Offline Status line in Settings ("Handa offline — naka-save ang account at mga scan mo sa phone na ito") and remove the scary "Password-only sign-in" amber box from login.tsx.
4

Address Farmer 30-Day Offline Expiry & Update Copy / Security Docs

Ensure a farmer who stays offline in remote areas for >30 days isn't abruptly locked out of their own local personal scan history and on-device AI scanner.

  • Single-source all new English & Tagalog copy in src/constants/copy.ts (replacing "weaker protection" and biometric-only phrasing with plain language: "Offline access" / "App lock").
  • Confirmed Farmer Personal-Scan Offline Grace Mode: When a farmer's token expires after 30 days offline, keep their local owner identity hydrated in read/scan grace mode so they can still open past scans and run on-device AI checks without being kicked to /login. Show a quiet bilingual banner asking them to sign in again when online for account/server features. Zero backend changes required.
  • Update docs/security/mobile-security-fixes.md (#70) and PROJECT_CONTEXT.md to truthfully document the updated storage & lock boundary.

Section 7 · Risks, Security & Edge Cases

What could go wrong — and how the plan guards against it

Security Boundary Update (#70)

Shared or Lost Field Phone

Risk: If an inspector loses a phone with no lock, someone could open CaneGuard and view cached visit addresses/photos or draft a fake report.
Mitigation: Under recommended Option C, inspector cold-start always uses OS Lock or 4-digit Quick PIN (5-try lockout wipes token). Explicit Logout immediately revokes server token + wipes SecureStore. Server /me revocation clears access on next signal.

User Forgets 4-Digit Quick PIN Offline

Risk: A user forgets their CaneGuard Quick PIN.
Mitigation: Unlock screen always shows "Sign in with password instead". After 5 failed PIN entries, the stored token is wiped (local SQLite drafts/scans remain intact for the owner!) and a fresh password sign-in online resets the PIN cleanly.

Existing Users Upgrading the App

Risk: Inspectors who already enabled biometric/device unlock could get silently signed out or lose their preference on app update.
Mitigation: On bootstrap, if PROTECTED_SESSION_KEY + BIOMETRIC_ENABLED_KEY === 'true' exist, auto-read as localLockMode = 'device' and keep the session alive. Zero forced logouts on upgrade.

User Removes OS Screen Lock Later

Risk: User had Phone PIN enabled, then removes their phone lock in Android Settings while offline.
Mitigation: Today this wipes the session and locks them out! With the new model: if OS lock disappears, detect gracefully — for Farmer (Option C) or Option A fall back cleanly; for strict Inspector lock, prompt to sign in with password or set Quick PIN instead of crashing with opaque Keystore error.

Inspector 72h Carry-Over vs. Persistence

Edge Case: Staying signed in does NOT mean unlimited offline inspector authoring.
Guard: Keep the server-offset CARRYOVER_WINDOW_MS (72h) for finalizing official Field Reports / Visits. When it expires offline, the user still stays signed in, can view all saved work, and sees one clear message: "Connect to confirm office access before finalizing."

Rollback & Backwards Compatibility

Safety: Because this requires zero backend contract changes and preserves SQLite schemas untouched, rolling back simply reverts the client auth store logic. All local scans, reports, and outbox items remain completely intact across upgrades or rollbacks.
